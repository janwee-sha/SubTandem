# Bug 评估：真实字幕轨语言检测失真

- **Slug**：`subtitle-language-detection`
- **创建日期**：2026-09-02
- **来源**：用户粘贴文本与四个本地媒体样本
- **结论**：valid
- **严重程度**：high

## 报告

四个本地媒体样本出现字幕语言无法可靠检测的问题，覆盖 ASS、`mov_text` 与 SubRip 文本字幕。

四个样本位于不纳入版本控制的本地目录。为避免受版本管理的评估依赖本地文件，本文按用户给出的顺序将其记为 A–D，只记录可复核的容器、codec、cue 与检测统计；修复前必须把有明确许可和真值的最小语料纳入版本控制。

## 症状

生产提取器能读取四个样本的 ASS、`mov_text` 与 SubRip 字幕，但多条正文明确、文字量充足的轨道仍返回 `unknown`，因而不会进入翻译流程；另有一条标记为日语的罗马字 ASS 轨被可靠判为豪萨语，可能以错误源语言方向调用 Provider。

“四个文件的所有轨道均无法检测”并不准确：样本 B 的英语轨和样本 C 的部分轨道可可靠识别。不过短轨漏检、真实中等长度轨漏检及一项可靠误判均已由生产路径复现，因此底层缺陷有效。

## 复现

1. 使用正式构建的 `subtandem-subtitle-extractor` 逐轨提取四个样本，不读取或信任轨道语言标签来决定结果。
2. 使用生产 `parseSrt`、`sampleSubtitleCues` 与 `detectSubtitleLanguage` 处理提取结果。
3. 仅为核对预期语言，另行读取容器标签；标签不参与生产检测。
4. 得到以下结果：

| 样本 | 生产提取与采样 | 生产检测结果 |
| --- | --- | --- |
| A：MKV / ASS | 38 个 cue，37 个有效 cue，651 个字母；四窗口第一名依次为 `eng/fra/swh/eng` | `unknown`，因只有两个窗口与总样本 `eng` 一致 |
| B：MP4 / `mov_text` | 第 3 轨为 11 个 cue、332 个字母，四窗口均为 `deu`；第 4 轨为 13 个 cue、382 个字母 | 第 3 轨被 `MIN_CUES=12` 直接判为 `unknown`；第 4 轨可靠识别为 `en` |
| C：MKV / ASS | 16 条文本轨，每轨 5–29 个 cue；其中 14 条有容器语言标签 | 7 条可靠、9 条 `unknown`；标记为 `jpn` 的 29-cue 罗马字轨被可靠误判为 `ha` |
| D：MKV / SubRip | 8 条文本轨，每轨仅 5–6 个 cue，过滤后为 3–6 个有效 cue、13–130 个字母 | 全部因固定下限返回 `unknown` |

样本 C 中，带标签轨道只有荷兰语、法语、德语、波兰语、葡萄牙语和西班牙语可靠且与标签一致；芬兰语、希伯来语、匈牙利语、意大利语、挪威语、俄语和瑞典语返回 `unknown`，日语轨误判为豪萨语。轨道标签只用于本次真值交叉检查，不构成建议中的生产兜底。

当前聚焦测试 `tests/unit/language-detection.test.ts` 与 `tests/integration/acceptance-metrics.test.ts` 共 12 项全部通过，说明现有质量门未覆盖上述真实分布。

## 涉及代码路径

- `native/subtitle-extractor/Sources/SubTandemSubtitleExtractor/Extractor.swift:20` — 四种样本均能通过生产解码与 SRT 渲染，排除统一的容器或 codec 提取故障。
- `src/subtitles/source.ts:66` — 校验提取结果并调用生产 `parseSrt`；本次所有成功提取轨均无解析警告且 cue 数与 helper 元数据一致。
- `src/subtitles/language-detection.ts:47` — 固定四等分采样使 19-cue 真实轨每窗只有 4–5 条，局部短句误分类会直接影响窗口一致性。
- `src/subtitles/language-detection.ts:118` — 对 `franc-min` 相对分数执行 50 次幂后再应用固定分差；其校准未挡住罗马字日语到豪萨语的可靠误判。
- `src/subtitles/language-detection.ts:124` — `MIN_CUES=12`、`MIN_LETTERS=200`、至少 3 个匹配窗口与 80% 加权支持率共同造成短轨和中等长度真实轨漏检。
- `tests/fixtures/languages/acceptance.json:2` — 验收语料明确是合成语料，每种语言只有 4 个整句模板。
- `tests/integration/acceptance-metrics.test.ts:40` — 将 4 个模板循环 5 次生成 20 个 cue，窗口天然重复且稳定，无法代表短对白、歌词、罗马字、专名和时间段噪声。

## 根因假设

置信度：高。问题不在内嵌字幕提取，而在检测器校准和验收语料的共同偏差。硬编码 cue 下限会拒绝文字量充足、四窗口一致的 5–11 cue 轨；固定四窗口门禁会放大真实短句的局部分类波动；基于 4 个干净整句反复复制的合成验收集又使这些缺陷无法进入指标。与此同时，50 次幂分差和 3/4、80% 门禁仍允许罗马字日语在三个窗口稳定误落到豪萨语后成为 `reliable`。因此当前策略同时出现高漏检和非零错误可靠结果，不能再仅按“短字幕符合现有阈值”关闭。

## 建议处置

**首选**：将修复作为新的有界完整 SDD 功能处理，因为可靠结果会决定 Provider 请求方向。先建立有明确许可、人工确认真值且纳入版本控制的真实字幕验收集，按短轨（5–11 cue）、中等轨（12–30 cue）、长轨、共享文字、罗马字/歌词、混合语言和 ASS 样式分层；质量门必须分别统计正确可靠率、`unknown` 率和错误可靠率，不得再用少量整句循环扩充 cue 数。

在该冻结语料上重新选择并校准离线检测策略：以有效文字量、可用窗口数和跨窗口证据共同决定短轨是否足够，不再单独以 12 个 cue 一票否决；重新评估 `franc-min`、完整 `franc` 或等价离线实现的真实字幕表现；只有 held-out 验收仍满足正确可靠率与错误可靠率门禁时才调整 `MIN_CUES`、分数变换、窗口支持率或候选集合。罗马字日语样本至少必须失败关闭为 `unknown`，不得可靠输出 `ha`。轨道元数据可作为测试真值或冲突观测，生产逻辑不得把它作为正向语言兜底。

**备选方案**：

- 仅降低 `MIN_CUES`：可恢复部分短轨，但不会修复样本 C 的窗口漏检和日语到豪萨语误判，不可单独采用。
- 用轨道 `lang` 直接兜底：会把缺失或错误元数据变成错误 Provider 方向，违反正文优先和失败关闭契约，不建议采用。
- 恢复手动源语言：会重新引入已移除的产品流程，属于独立用户能力，不能作为本 bug 的局部补丁。

**预计修改文件**：

- 新的有界 SDD 规格目录，由 `specify` 阶段分配编号
- `src/subtitles/language-detection.ts`
- `src/domain/target-languages.ts`（仅当检测 profile 覆盖范围改变）
- `tests/fixtures/languages/`
- `tests/unit/language-detection.test.ts`
- `tests/integration/acceptance-metrics.test.ts`
- `package.json`、`package-lock.json`、`THIRD_PARTY_NOTICES.txt`（仅当更换检测依赖）

**测试建议**：

- 增加 11-cue、332 字母且四窗口一致的德语短轨，验证在新门禁下得到正确可靠结果。
- 增加 5–6 cue 的拉丁文字与高区分 script 短轨，分别校准可可靠与必须 `unknown` 的边界。
- 增加 19-cue 的自然匈牙利语、意大利语、俄语和瑞典语轨，防止单个噪声窗口造成系统性漏检。
- 增加罗马字日语/歌词与混合 ASS 负样本，断言不得可靠输出无关语言且 Provider 调用为 0。
- 用独立 calibration/acceptance 语料重新验证 ≥95% 正确可靠、≤1% 错误可靠、零错误方向 Provider 调用和既有性能门禁。
- 每次代码变更后重新执行测试、编译和正式打包校验；不得沿用变更前结果。

## 风险与注意事项

- 直接放宽短轨门禁会扩大误判面，并可能以错误源语言方向发送用户已选择翻译的字幕。
- 更换或扩大离线模型会增加 `dist/main.js`、正式包体积、首次识别耗时和第三方许可工作。
- 目标语言目录有 156 项，但当前 `franc-min` 只覆盖其中一部分；修复必须明确“可检测源语言”范围，不能把目标语言可选误当成源语言可识别。
- 容器语言标签本身可能错误；任何纳入冻结语料的真值都必须人工核对正文，而不是自动接受标签。
- 四个本地媒体只能作为诊断证据，受版本管理的测试和文档不得依赖被忽略的本地路径。
