# 研究与技术决策：渐进式字幕翻译输出

## Provider 增量边界

**决策**：`TranslationProvider.attempt` 接受可选的同步 `onProgress` 回调。每个 wire 请求完成本地验证并恢复原始 cue ID 后，回调一次且只携带该 wire 请求中新验证的译文；attempt 终态继续返回完整聚合结果。

**理由**：增量与 provider 内部的 wire 拆分边界一致，Main 无需理解具体服务协议；可选回调保持 fake 或第三方 provider 的终态兼容。

**考虑过的替代方案**：异步生成器会改变所有调用方和取消语义；把回调塞入可序列化请求会污染 Main→Global 消息；只返回部分异常会失去实时性。

## 部分成功与重试所有权

**决策**：Main 在进度到达时立即验证当前 attempt 身份、写缓存并从 `remaining` 移除 cue。终态聚合结果沿同一路径去重；后续错误和部分终态只对 `remaining` 使用现有最多三次额外重试。

**理由**：Main 已拥有会话、缓存和重试策略，能够在不重放成功字幕的前提下保持原有错误分类与退避边界。

**考虑过的替代方案**：让 Global 或 provider 跨 attempt 保存部分状态会共享播放器状态并扩大秘密数据寿命；重试整个逻辑批次会重复外发和计费。

## Global 消息路由

**决策**：新增 `provider:attempt-progress`。Global 的 broker 仅在权威 player ID 与 request ID 对应的活动 attempt 尚未终态或取消时转发；Main 的 pending entry 在终态 resolve/reject 前删除，并只把进度交给该 entry 的回调。

**理由**：复用现有每窗口消息通道和 request ID 相关性，同时在 Global 与 Main 两端都关闭迟到事件入口。

**考虑过的替代方案**：广播进度再由 controller 筛选会扩大跨窗口泄漏面；只依赖 payload 中的 player ID 可被伪造；终态后保留 handler 容易接受迟到事件。

## 单飞字幕发布

**决策**：每个 `PlaybackController` 维护一个在途发布和一个最新待发布快照。首个快照立即启动 `swap`；在途期间的新快照覆盖待发布槽；完成后继续处理最新槽。所有快照携带播放指纹，发布前后都检查当前性。

**理由**：IINA 的加载与选轨包含异步稳定期，并发 `swap` 会竞争自有轨道和主/次字幕选择；最新覆盖可控制 I/O 并保证最终显示当前完整状态。

**考虑过的替代方案**：每个进度并发替换会产生轨道竞争；逐个排队会发布已过时中间态并放大延迟；只在终态发布就是当前缺陷。

## 生命周期与失效发布

**决策**：跳转、换轨、换片、Profile 变化、禁用或关闭会清除待发布快照并使旧指纹失效。无法取消的旧 `swap` 完成后再次检查指纹；若已失效则清理插件自有轨道，不修改当前状态。

**理由**：IINA 轨道加载不能可靠中止，完成后补偿清理是防止迟到轨道污染的必要边界。每窗口发布串行使清理不会与同窗口的新快照并发。

**考虑过的替代方案**：仅在进度入口检查无法处理已启动的迟到 `swap`；在轨道管理器内持有播放会话会混合适配器与产品状态。

## 取消后的 provider 行为

**决策**：OpenAI-compatible 与 Ollama 记录已取消逻辑 request。transport 返回后、验证和上报前检查取消状态；取消后的 attempt 以稳定的 cancelled 错误终结且不再上报进度。

**理由**：底层取消可能与响应完成竞争，仅调用 transport cancel 不能证明不会产生迟到回调。

**考虑过的替代方案**：只依赖 Main 丢弃虽然能保护缓存，但无法满足 provider 契约，也会在 Global 产生无用进度消息。
