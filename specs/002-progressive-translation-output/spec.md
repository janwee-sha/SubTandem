# 功能规格：渐进式字幕翻译输出

**功能目录**：`specs/002-progressive-translation-output`
**创建日期**：2026-08-12
**状态**：草案
**输入**：修复密集字幕必须等待整个逻辑批次完成才显示译文的问题，使已验证的部分结果能安全、渐进地进入当前播放会话。

## 用户场景与测试

### 用户故事 1：尽早看到已完成的译文（优先级：P1）

用户播放密集的外挂字幕时，希望最先完成的有效译文立即进入缓存并显示为第二字幕，而不是等待同一逻辑批次的所有服务请求结束。

**优先级理由**：当前延迟直接导致界面长期停留在“准备中”、缓存为 0 且第二字幕无输出，是本次修复的首要用户结果。

**独立测试**：使用包含 25 个相邻 cue 的合成字幕，让第一个子请求成功并阻塞后续请求；首个结果应在后续请求结束前进入缓存并开始发布第二字幕。

**验收场景**：

1. **假如** 一个 25 cue 的逻辑批次被拆成 13 个服务请求，**当** 第一个请求返回有效译文且其余请求仍阻塞，**那么** 缓存立即增加并开始发布包含这些译文的第二字幕。
2. **假如** 多个有效结果快速连续到达，**当** 前一个字幕替换仍在执行，**那么** 同一窗口不并发替换，并在完成后发布最新有效快照。
3. **假如** 首个当前会话快照成功显示，**当** 后续子请求仍在处理，**那么** 会话状态不再停留在“准备中”，视频和原字幕始终不中断。

---

### 用户故事 2：保留成功结果并只重试未完成 cue（优先级：P2）

用户遇到逻辑批次中途失败时，希望已经成功的译文继续可见且不被重复发送，只对仍未解决的 cue 执行现有受限重试。

**优先级理由**：保留已完成工作可以缩短恢复时间、避免重复费用并维持字幕内容最小外发原则。

**独立测试**：让前两个子请求成功、第三个请求发生可重试错误，记录后续请求中的 cue ID；重试中不得出现已成功 cue，成功译文仍在缓存和最新字幕快照中。

**验收场景**：

1. **假如** 一个逻辑批次已有部分 cue 成功，**当** 后续子请求发生临时错误，**那么** 已成功 cue 保留且后续重试只包含未解决 cue。
2. **假如** 同一 cue 同时出现在进度和终态聚合结果中，**当** 两者依次到达，**那么** 缓存、字幕和重试集合只接受该 cue 一次。
3. **假如** 子请求返回未知、重复、空白或无法映射的结果，**当** 结果被检查，**那么** 无效项不进入进度、缓存或字幕。

---

### 用户故事 3：生命周期变化后不接受迟到进度（优先级：P3）

用户跳转、换轨、换片、切换服务、禁用翻译或关闭窗口后，希望旧工作的进度和字幕替换都不能污染当前会话或其他窗口。

**优先级理由**：渐进事件增加了异步完成点，必须继续满足现有的会话、隐私和多窗口隔离边界。

**独立测试**：在首个子请求完成前后分别触发跳转、换轨、换片、服务切换、禁用和关闭，再释放迟到结果；当前缓存、状态和第二字幕不得被旧身份修改，失效的插件自有轨道被清理。

**验收场景**：

1. **假如** 旧请求仍在执行，**当** 当前播放窗口的会话、跳转窗口或服务选择发生变化，**那么** 旧进度和终态结果均被拒绝。
2. **假如** 两个窗口使用相同请求 ID，**当** 任一窗口收到进度或终态事件，**那么** 事件只作用于 IINA 标识的所属窗口。
3. **假如** 字幕替换执行期间会话失效，**当** 迟到替换完成，**那么** 失效的插件自有字幕轨被清理，且不会删除用户拥有的轨道。

### 边界情况

- 单个逻辑批次只有一个 wire 请求时，进度与终态结果不得造成重复缓存或重复发布。
- 不产生进度事件的兼容 provider 仍可通过终态结果完成翻译。
- 取消与终态结果之后到达的进度不得进入 Main，也不得触发新的字幕替换。
- 字幕发布失败时，已验证译文仍保留在会话缓存中，状态显示为部分失败。
- 快速进度到达速度高于 IINA 加载字幕轨的速度时，只保留最新待发布快照。

## 需求

### 功能需求

- **FR-001**：每个已验证的 wire 子请求完成后，系统 MUST 立即把其中新成功的 cue 作为增量进度交给所属逻辑批次，不等待其余子请求。
- **FR-002**：增量进度 MUST 在恢复原始 cue ID 并完成请求集合、唯一性和非空文本验证之后产生；无效项 MUST NOT 进入进度。
- **FR-003**：逻辑批次的终态成功 MUST 继续提供完整聚合结果；不产生进度的 provider MUST 保持可用。
- **FR-004**：Main MUST 只接受与当前 player、session、session/window epoch、Profile ID/revision、endpoint fingerprint、batch ID 和 request ID 完全匹配的进度。
- **FR-005**：每个被接受的新 cue MUST 立即写入当前会话缓存、从未解决集合移除，并推动当前译文快照发布。
- **FR-006**：进度与终态结果重复包含同一 cue 时，系统 MUST 去重；已经成功的 cue MUST NOT 出现在后续重试请求中。
- **FR-007**：逻辑批次后段失败时，系统 MUST 保留已验证并缓存的译文，并只按现有策略重试未解决 cue。
- **FR-008**：同一窗口同时 MUST 最多执行一次插件字幕轨替换；替换期间 MUST 只保留最新待发布快照。
- **FR-009**：首个当前会话快照成功显示后状态 MUST 转为运行中；发布失败 MUST 显示部分失败且 MUST NOT 撤销已验证缓存。
- **FR-010**：取消、终态完成或任何会话生命周期失效之后，系统 MUST 丢弃对应迟到进度；失效替换产生的插件自有轨道 MUST 被清理。
- **FR-011**：Global MUST 按 IINA 提供的权威 player ID 和 request ID 路由进度，并在请求终态或取消时清理进度路由状态。
- **FR-012**：进度消息和诊断 MUST NOT 包含凭据、授权头、provider 原始响应或超出当前有效 cue 增量的字幕数据。
- **FR-013**：现有 120 秒或 40 cue 前瞻、25 cue 或 5,000 字符逻辑批次、每个 wire 请求最多 2 cue，以及首次尝试后最多 3 次重试的边界 MUST 保持不变。
- **FR-014**：外挂字幕仍 MUST 由用户在 IINA 中手动加载和选择；本功能 MUST NOT 自动加载字幕或读取内嵌字幕。

### 关键实体

- **翻译批次进度**：属于单个逻辑请求的一组新验证译文，带有可验证的 player、会话、窗口、Profile、批次和请求身份。
- **未解决 cue 集合**：当前逻辑批次中尚未被有效进度或终态结果满足、可参与后续重试的 cue。
- **发布快照**：当前会话所有已验证译文渲染出的完整第二字幕内容，带所属生命周期身份。
- **发布协调器**：同一窗口内至多一个在途替换和至多一个最新待发布快照。

### 范围边界

**范围内**：OpenAI-compatible 与 Ollama 的逐 wire 进度、Global→Main 路由、Main 增量缓存与重试、单飞字幕发布、生命周期隔离和自动化回归。

**范围外**：自动加载外挂字幕、提取内嵌字幕、扩大前瞻或批次边界、持久化译文、修改 provider 重试上限或改变用户的字幕轨选择流程。

## 成功标准

### 可度量结果

- **SC-001**：25 cue 逻辑批次稳定拆成 13 个 wire 请求时，第一个有效请求完成后即增加缓存并开始第二字幕发布，无需等待其余 12 个请求终结。
- **SC-002**：任意中途失败场景中，已成功 cue 在后续 provider 调用中的重复次数为 0，且缓存命中和已发布译文保持有效。
- **SC-003**：同一窗口在任意快速进度序列中观测到的最大并发字幕轨替换数为 1，空闲后的最终内容等于最新有效快照。
- **SC-004**：跳转、换轨、换片、服务切换、禁用和关闭场景中，迟到进度对当前缓存、状态和字幕的写入次数均为 0。
- **SC-005**：现有前瞻、批次、wire 大小与重试边界的自动化断言全部保持通过。
- **SC-006**：OpenAI-compatible 与 Ollama 均通过逐请求进度、完整终态聚合、部分成功后失败、取消后无进度和无效结果过滤的契约测试。

## 假设

- 现有外挂 SRT/ASS 读取、语言门控、会话缓存和 Profile 授权模型继续作为前置能力。
- provider 进度回调是进程内同步通知，不等待字幕轨发布，也不改变 provider 的最终返回类型。
- IINA 的字幕轨加载无法安全并发，因此每个播放器窗口独立串行发布；不同窗口仍可并发。
- 实机验收使用用户自行准备且可合法用于测试的本地视频与对应外挂字幕夹具；用户仍需在 IINA 中手动加载并选择外挂字幕，且不得把媒体路径、字幕正文、凭据或 provider 原始响应写入证据。
