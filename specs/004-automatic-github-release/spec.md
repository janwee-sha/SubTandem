# 功能规格：自动 GitHub Release

**功能目录**：`specs/004-automatic-github-release`  
**创建日期**：2026-08-14  
**状态**：已完成  
**输入**：远程 `main` 每次推送都执行完整发布门禁；首次出现的新稳定版本在门禁通过后自动创建不可覆盖的普通 GitHub Release，同版本后续推送只验证并安全跳过。

## 用户场景与测试

### 用户故事 1：新版本自动正式发布（优先级：P1）

维护者把包含新稳定版本的提交推送到远程 `main` 后，希望系统完整验证源码和最终安装包，并立即创建可下载、可校验且可追溯到该提交的正式 Release。

**优先级理由**：自动形成可信正式产物是本功能的核心价值。

**独立测试**：在不存在对应 tag 和 Release 的版本上触发流程；全部门禁通过后，应只创建一个普通 Release，tag 指向触发提交并标记为 Latest，正文来自 009 版本化用户说明，四项资产与技术证据完整。

**验收场景**：

1. **假如** `main` 中出现新的合法稳定版本且全部门禁通过，**当** 自动流程完成，**那么** 唯一的 `vX.Y.Z` tag 指向触发提交，并产生一个非 draft、非 prerelease、标记 Latest 的 Release。
2. **假如** 最终安装包已经生成，**当** 发布前审计运行，**那么** 文件名、包内版本、根目录、敏感或开发文件、路径安全和 native helper 属性全部符合发布契约。
3. **假如** 发布成功，**当** 下载者查看 Release，**那么** 可获得安装包、安装包校验、锁定 FFmpeg 源码及源码校验四项资产和英文用户说明；维护者可在审计 JSON、Actions 摘要与日志中核对触发提交、八项门禁及归档内容。

---

### 用户故事 2：未提升版本时安全验证（优先级：P2）

维护者在已经发布的版本上继续推送代码时，希望仍运行全部门禁，但不覆盖、移动或修改已有 tag、Release 和资产。

**优先级理由**：持续验证不能破坏既有正式版本的不可变性。

**独立测试**：让目标版本已经存在公开 Release，再触发相同版本流程；门禁应全部执行，发布阶段应成功跳过且已有 Release 保持逐字节不变。

**验收场景**：

1. **假如** 当前版本已有公开 Release 且正文与对应版本化用户说明一致，**当** 相同版本的 `main` 推送或手动重试通过门禁，**那么** 流程成功结束且不修改任何已有发布对象。
2. **假如** 任一项目版本来源不一致、版本不是稳定 `X.Y.Z` 或版本化用户说明无效，**当** 流程读取发布元数据，**那么** 在构建 Release 前失败并报告不一致来源。

---

### 用户故事 3：失败与重试不公开残缺版本（优先级：P3）

维护者希望任一门禁、下载校验、归档审计或上传失败都不会公开残缺 Release；同一提交重跑时可以安全继续未完成的 draft。

**优先级理由**：发布失败必须保持公开下载面的完整和不可覆盖。

**独立测试**：分别制造门禁失败、IINA 下载校验失败、归档异常、上传中断和重复执行；公开 Release 数量不得增加，匹配提交的 draft 可恢复，冲突 draft 或资产必须失败而非覆盖。

**验收场景**：

1. **假如** 八项门禁或最终归档审计任一失败，**当** 流程终止，**那么** 不创建公开 Release。
2. **假如** 资产上传中断并留下 draft，**当** 相同版本与提交重跑，**那么** 已上传的同内容资产被保留，缺失资产补齐后才公开。
3. **假如** draft、tag 或同名资产与当前版本、提交或内容冲突，**当** 流程重跑，**那么** 流程失败且不覆盖冲突对象。
4. **假如** 同版本流程并发或重复执行，**当** 所有执行结束，**那么** 最多存在一个 tag、一个 Release 和一组资产。

### 边界情况

- 手动重试只能以 `main` 为目标；其他分支不得进入构建或发布任务。
- IINA v1.4.4 下载内容与固定 SHA-256 不一致时，全部后续门禁停止。
- 归档中的绝对路径、`..`、反斜线、重复路径、符号链接、禁用文件或非白名单根目录均视为失败。
- 构建文件或包内 native helper 任一缺少 `arm64`、`x86_64`、可执行权限或有效签名时，归档不得发布。
- 已公开的同版本 Release 无论其 tag 是否指向当前后续提交，都只允许安全跳过，不允许移动 tag。
- 已公开正文与对应版本化用户说明不一致时必须冲突失败，不得编辑正文或其他远端对象。

## 需求

### 功能需求

- **FR-001**：每次远程 `main` 推送必须运行完整发布流程，并提供仅允许 `main` 的手动重试入口。
- **FR-002**：发布元数据必须验证 `Info.json`、`package.json`、`package-lock.json` 两处项目字段及打包产物路径中的版本完全一致，且版本符合稳定 `X.Y.Z`。
- **FR-003**：发布流程必须严格依次通过测试、类型检查、代码检查、native 构建、native 测试、插件构建、包验证和正式打包八项门禁。
- **FR-004**：流程必须固定使用 IINA v1.4.4，并在调用其打包工具前验证下载内容的指定 SHA-256。
- **FR-005**：最终归档必须独立复核包内版本、产物名、根目录白名单、禁用文件、路径穿越、重复路径和符号链接。
- **FR-006**：构建文件与包内 native helper 必须分别验证 `arm64`、`x86_64`、可执行权限和签名。
- **FR-007**：新版本 Release 的 `vX.Y.Z` tag 必须指向触发流程的精确提交；已有 tag、Release 或资产不得被覆盖或移动。
- **FR-008**：Release 必须为普通非 prerelease，并在发布完成时标记 Latest。
- **FR-009**：Release 必须提供 `SubTandem-X.Y.Z.iinaplgz`、同名 `.sha256`、锁定 FFmpeg 源码及其 `.sha256` 四项资产；正文必须采用 009 定义并经审计的版本化用户说明。
- **FR-010**：版本已公开发布时，流程必须在全部门禁通过后比较正文；一致时成功跳过，偏差时冲突失败，且不得修改现有发布对象。
- **FR-011**：流程必须先创建 draft、补齐并核对全部资产，再公开 Release；任一前置失败不得产生公开残缺版本。
- **FR-012**：匹配版本、提交和正文的 draft 必须可恢复；已有同名资产只有内容完全一致时才可复用，任何冲突必须失败。
- **FR-013**：构建任务只具备读取仓库内容的权限，独立发布任务才可获得写入 Release 所需权限；不得使用 PAT 或第三方发布 Action。
- **FR-014**：技术发布证据必须保留在校验文件、`release-audit.json`、Actions 摘要与日志中，不得混入用户正文；流程不得为证据回写仓库或递归推送 `main`。
- **FR-015**：审计 JSON 与 Actions 证据必须明确 IINA 图形界面中的真实安装、卸载和播放未由 CI 覆盖，且该状态不阻塞正式发布。

### 关键实体

- **发布版本**：由一致的稳定版本、tag、触发提交和产物名组成的不可变发布身份。
- **归档审计结果**：最终归档的版本、大小、哈希、条目清单和两份 native helper 属性。
- **版本化用户说明**：由 009 定义的正文来源，以路径与原始摘要绑定同一发布版本。
- **发布草稿**：资产上传期间的非公开状态，只能由相同版本、触发提交和正文恢复。

## 成功标准

### 可度量结果

- **SC-001**：新版本通过全部门禁后只产生 1 个公开稳定 Release、1 个 tag 和 4 个下载资产，tag 精确指向触发提交。
- **SC-002**：相同已发布版本重复触发 1 次或并发触发多次时，已有 tag、Release 和资产的修改次数均为 0。
- **SC-003**：八项门禁、IINA 下载校验或归档审计任一失败时，新增公开 Release 数量为 0。
- **SC-004**：上传中断重跑后，内容相同的已上传资产覆盖次数为 0，缺失资产补齐后 Release 才公开。
- **SC-005**：非法 SemVer、五个版本位置不一致、产物名或包内版本不一致、禁用路径、路径穿越、重复路径、符号链接和 native 属性缺失均有自动失败回归。
- **SC-006**：每次发布的审计 JSON 与 Actions 证据完整列出 8 项门禁、全部归档条目、构建/包内 helper 验收结果及 3 类 IINA 图形界面未覆盖状态，用户正文中技术证据字段出现次数为 0。

## 范围边界

- 不修改插件运行时 API、消息结构、配置类型、网络目的地或持久化数据。
- 不新增 prerelease、人工提升、Developer ID 签名或公证；IINA 客户端更新发现由 [012](../012-iina-auto-update/spec.md) 负责。
- Native helper 继续使用现有 ad-hoc 签名策略。
- CI 通过即构成自动发布门槛；IINA 图形界面实机行为不作为 Release 前置条件。

## 假设

- GitHub Actions 已启用，仓库或组织策略允许发布任务申请 `contents: write`。
- GitHub 托管的 `macos-15` runner 为 Arm64，并提供完成 Swift 双架构构建所需工具。
- IINA v1.4.4 官方资产为 `IINA.v1.4.4.dmg`，其 SHA-256 为 `dd0fc0bd4b37fb57a1c8d30d6e3201b3a64bafd29959fe56953964613237beb1`。
