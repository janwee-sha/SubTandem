# 功能规格：版本化用户发布说明

**功能目录**：`specs/009-versioned-release-notes`

**创建日期**：2026-08-17

**状态**：已完成

**输入**：将每个版本的 GitHub Release 英文正文作为受版本控制的用户发布说明保存，正文只描述最终用户可感知的功能变化，并与技术发布证据分离。

## 用户场景与验收

### 用户故事 1：用户快速理解版本变化（优先级：P1）

用户查看 SubTandem 的正式 GitHub Release 时，可以直接了解本版本新增、改进或修复了什么，以及升级前需要注意的兼容条件，而不必从构建结果或技术审计数据中自行判断。

**优先级理由**：Release 正文首先服务于下载和升级用户，清晰说明可感知变化是本功能的核心价值。

**独立验收**：开发者发布版本后核对公开正文只呈现已验收的用户变化，且与该版本的仓库文档内容一致。

**验收场景**：

1. **假如** 某版本包含已验收的新功能、功能改进或问题修复，**当** 用户查看公开 Release，**那么** 正文按有内容的对应章节说明用户场景、可感知变化及必要条件。
2. **假如** 某版本存在升级限制或兼容性影响，**当** 用户阅读正文，**那么** 可以在“升级与兼容提醒”中识别影响范围和需要采取的操作。
3. **假如** 某版本没有面向用户的行为变化，**当** 用户查看公开 Release，**那么** 正文明示 `This release contains no user-facing behavior changes.`，且不以内部技术工作充当功能变化。

---

### 用户故事 2：维护者按版本保存权威正文（优先级：P2）

维护者可以在发布前根据用户指定的一项或多项功能规格，创建与目标版本一一对应的英文发布说明，并通过版本历史长期查看每个版本当时采用的正文。

**优先级理由**：稳定且可追溯的正文来源可以避免发布阶段临时生成、丢失或改变功能范围。

**独立验收**：开发者在发布前核对目标版本只有一个对应文件，文件名、标题和版本一致，且各条变化都能追溯到指定规格。

**验收场景**：

1. **假如** 用户明确提供目标版本及对应的已验收规格，**当** 维护者准备发布，**那么** `docs/releases/vX.Y.Z.md` 只收录这些规格支持的用户可感知变化。
2. **假如** 多项规格共同组成一个版本范围，**当** 发布说明完成，**那么** 所有已验收的用户变化均被覆盖，且没有从未指定的规格、commit、PR 或 issue 扩大范围。
3. **假如** 指定规格含有未验收内容，或规格与当前交付状态实质不一致，**当** 维护者准备发布说明，**那么** 该版本被报告为尚未具备发布条件，不把未交付内容写成已发布功能。
4. **假如** 已存在多个适用本契约的公开版本，**当** 维护者按版本号查找，**那么** 每个版本都能定位到唯一的版本化发布说明。

---

### 用户故事 3：失败关闭且保留技术证据（优先级：P3）

维护者希望缺失、错版或内容冲突的用户发布说明能够阻止新版本公开，同时原有安装包审计、校验和发布门禁证据继续独立保留。

**优先级理由**：正文质量不能以削弱发布可信度为代价，错误正文也不能随正式版本公开。

**独立验收**：发布脚本在运行时校验版本化正文；现有发布安全回归继续确认远端正文冲突不会覆盖 draft 或公开 Release，技术证据仍可独立核对。

**验收场景**：

1. **假如** 新版本的发布说明缺失、为空或版本身份不一致，**当** 发布流程运行，**那么** 在公开 Release 前失败并指出对应问题。
2. **假如** 待恢复 draft 的正文与该版本的权威发布说明不一致，**当** 流程重试，**那么** 拒绝恢复且不覆盖远程正文。
3. **假如** 用户发布说明合法且其他发布门禁全部通过，**当** 新版本公开，**那么** Release 正文来自该版本文件，技术证据继续在独立证据中保留且不混入正文。
4. **假如** 同版本已经公开发布，**当** 后续流程再次运行，**那么** 不修改已有 tag、Release 正文或资产；若版本化正文已产生偏差，则报告冲突而不是改写公开版本。

### 边界情况

- 文件名版本、一级标题版本、项目版本或目标 tag 任一不一致时，该发布说明无效。
- 只包含内部重构、测试、文档、构建、门禁或依赖维护的版本，按“没有面向用户的行为变化”处理，不把技术工作包装成用户功能。
- `New Features`、`Improvements`、`Bug Fixes` 和 `Upgrade and Compatibility Notes` 中没有内容的章节直接省略；同一变化不得跨章节重复表述。
- PR、issue 或 commit 链接可以作为补充追溯信息，但其标题和描述不能替代用户指定规格，也不能扩大版本范围。
- 已公开版本的正文保持不可变；后续发现措辞需要调整时，不通过相同版本的自动流程覆盖远程对象。
- 本功能生效前已经公开的历史 Release 不要求补写或改写；首次适用版本由发布准备时明确指定。

## 需求

### 功能需求

- **FR-001**：每个适用本契约的新稳定版本 MUST 在触发自动发布的提交中包含唯一的 `docs/releases/vX.Y.Z.md`，其中 `X.Y.Z` 与全部项目版本来源和目标 tag 完全一致。
- **FR-002**：版本化发布说明 MUST 以用户明确指定的一项或多项规格为功能范围来源；当前实现、测试和追溯记录只用于确认交付状态，MUST NOT 替代或扩大指定范围。
- **FR-003**：指定规格中的用户变化只有在已经实现并验收后才可写入发布说明；存在未验收范围或实质不一致时 MUST 阻止该版本进入正式发布。
- **FR-004**：发布说明 MUST 使用英文并面向最终用户，一级标题 MUST 为 `# SubTandem vX.Y.Z`。
- **FR-005**：发布说明只可保留有内容的 `New Features`、`Improvements`、`Bug Fixes` 和 `Upgrade and Compatibility Notes` 章节；每条 MUST 描述用户场景、可感知变化及必要的启用条件或限制。
- **FR-006**：版本没有用户可感知变化时，发布说明 MUST 在标题后明确写明 `This release contains no user-facing behavior changes.`，且 MUST NOT 创建空章节。
- **FR-007**：发布说明 MUST NOT 包含触发 commit、精确大小、SHA-256、归档清单、native helper 验收、自动化门禁结果或其他面向维护者的技术发布证据。
- **FR-008**：新版本的 GitHub Release 正文 MUST 直接采用对应版本化发布说明，不得在发布阶段根据 commit、PR、issue 或审计结果重新生成另一套功能范围。
- **FR-009**：发布前 MUST 验证版本化发布说明存在、非空、版本一致、章节合规且范围已经验收；任一校验失败时 MUST NOT 创建公开 Release。
- **FR-010**：已有 draft 只有在版本、目标提交和正文均与当前发布输入一致时才可恢复；正文冲突 MUST 失败并保留现场，不得覆盖。
- **FR-011**：已公开版本 MUST 继续保持不可变；相同版本后续流程不得修改 tag、正文或资产，版本化正文与公开正文不一致时 MUST 报告冲突。
- **FR-012**：技术发布证据 MUST 与用户发布说明分离，继续记录安装包身份、校验值、门禁和归档审计结果，并可追溯到同一版本、tag 和触发提交。
- **FR-013**：自动发布流程 MUST 只读取触发提交中已经存在的版本化发布说明，MUST NOT 生成、修改、提交或推送仓库文档。
- **FR-014**：除 Release 正文来源、内容校验和证据位置外，现有稳定版本发布门禁、安装包内容、资产完整性、权限边界、失败恢复及 Latest 规则 MUST 保持不变。
- **FR-015**：本功能 MUST NOT 追溯修改生效前已经公开的 Release，也 MUST NOT 改变插件运行时行为、字幕数据流、翻译服务、持久化数据或安装包内容。

### 关键实体

- **版本发布范围**：目标稳定版本、用户指定规格及其验收状态的集合，限定本版本可对外声明的用户变化。
- **版本化发布说明**：与单一稳定版本绑定的英文用户文档，包含固定版本标题、零个或多个允许章节及可追溯到发布范围的条目。
- **公开 Release 正文**：用户在 GitHub Release 中看到的版本变化说明，内容来自对应版本化发布说明，公开后保持不可变。
- **技术发布证据**：与同一版本关联的安装包身份、校验值、门禁和归档审计结果，仅用于验证发布可信度，不属于用户功能更新说明。

### 范围边界

**范围内**：按稳定版本保存英文用户发布说明、依据用户指定规格限定内容、发布前完整性与一致性校验、GitHub Release 正文采用该文件、技术证据分离、draft 冲突处理和已公开版本不可变。

**范围外**：自动从 commit、PR 或 issue 推断版本范围；修改插件运行时；改变安装包、发布资产、签名或门禁内容；新增 prerelease；追溯改写已有公开 Release；建立面向开发者的逐版本技术流水账。

## 成功标准

### 可衡量结果

- **SC-001**：本功能生效后的每个新公开稳定版本均有且只有 1 份版本化发布说明，文件版本、标题版本、项目版本、tag 和公开正文的一致率为 100%。
- **SC-002**：发布流程遇到缺失、空白、版本不一致、未验收范围、非法章节或 draft 正文冲突时，新增公开 Release 数量为 0，远程冲突对象修改次数为 0。
- **SC-003**：抽查每份发布说明的全部条目时，可追溯到用户指定且已验收规格的比例为 100%，无法证实或尚未交付的功能条目数为 0。
- **SC-004**：公开 Release 正文中触发 commit、精确大小、SHA-256、归档清单、native helper 验收和自动化门禁明细的出现次数为 0；这些技术证据的既有覆盖项保留率为 100%。
- **SC-005**：由开发者进行一次单人验收时，无需查看源码、提交记录或构建日志，即可在 2 分钟内从发布说明准确列出本版本的用户变化和全部升级兼容提醒。
- **SC-006**：相同已公开版本重复触发或版本化正文发生后续偏差时，已有 tag、Release 正文和资产的修改次数均为 0。

## 假设

- 本功能只适用于稳定版本 `X.Y.Z`；prerelease 和其他版本格式不在当前范围内。
- 发布准备开始前，用户会明确提供目标版本及其对应的一项或多项规格；缺少任一输入时不生成发布说明或执行发布。
- 已公开 Release 保持不可变；需要修正已发布说明时通过单独决策处理，不把相同版本覆盖能力纳入本功能。
- 历史 Release 不强制补写版本化文档，首次适用版本及对应规格由后续发布准备明确确定。
- PR、issue 和 commit 仅承担交付核对与补充追溯作用，版本功能范围以用户指定规格为准。
- 现有自动 GitHub Release 能力、正式包验证与技术审计继续作为本功能的依赖，并在本功能中只替换其正文来源和证据展示边界。
