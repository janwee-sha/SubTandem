# 版本化用户发布说明契约

## 身份与路径

- 只接受稳定版本 `X.Y.Z`。
- 权威文件路径必须由版本唯一派生为 `docs/releases/vX.Y.Z.md`，不得由调用者选择其他文档。
- 文件必须是已存在的普通 UTF-8 文本文件，不得为空、包含 BOM 或无效字符。
- 第一行必须精确为 `# SubTandem vX.Y.Z`，且不得出现第二个一级标题。
- 文件名、一级标题、全部项目版本和目标 tag 必须指向同一版本。

## 正文模式

标题之后只允许以下两种互斥模式。

### 变化模式

- 至少出现一个二级章节。
- 二级章节只允许 `New Features`、`Improvements`、`Bug Fixes`、`Upgrade and Compatibility Notes`，各最多一次，并按此相对顺序出现。
- 每个出现的章节必须至少包含一个以 `- ` 开始的非空顶层条目，每条必须使用英文。
- 条目可包含产品名、行内代码、强调和补充追溯链接，但必须保持单条用户变化语义。
- 不允许空章节、普通正文段落、嵌套列表、额外标题、代码块或章节外条目。

### 无变化模式

标题之后只能出现以下完整句子，不得再有章节或条目：

```text
This release contains no user-facing behavior changes.
```

## 内容边界

- 每条变化必须在发布准备阶段由用户指定且已验收的规格支撑；代码、测试、PR、issue 和 commit 只可用于确认交付状态或提供补充链接。
- 不得把内部架构、重构、测试、文档、构建、门禁或依赖维护描述为功能变化，除非只陈述其最终产生的用户行为、使用条件或兼容影响。
- 正文不得包含技术审计字段或段落，包括“触发提交”“包内版本”“精确大小”“SHA-256”“自动化门禁”“最终归档清单”“签名摘要”“构建文件”“IINA 图形界面验收边界”及三项 CI 未覆盖明细。
- 正文不得包含固定“自愿支持”章节；爱发电与 Ko-fi 入口继续由 README 和 GitHub Sponsor 承担。

自动校验只证明路径、版本、语法和显式技术证据隔离。规格来源、验收状态和措辞是否真正面向最终用户必须按发布准备流程进行一次开发者核对。

## 规范化与摘要

- 仓库文件、审计副本和审计 JSON 之间使用原始字节 SHA-256 比较，任何字节变化都失败。
- 与 GitHub 远端正文比较时，只把 CRLF 转为 LF 并移除正文末尾空白；正文内部的字符、行、章节、列表或空白差异仍视为冲突。
- 规范化只用于比较，不得改写仓库源文件或审计副本。

## 失败结果

缺失、空白、身份错配、非法结构、技术证据命中、初始摘要与最终摘要不一致或远端正文冲突时，流程必须失败并给出可定位原因。在第一次 GitHub 写操作前发生的失败，远端写入次数必须为零。
