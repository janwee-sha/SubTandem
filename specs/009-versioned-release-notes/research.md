# 研究与技术决策：版本化用户发布说明

## 权威正文与适用范围

**决策**：每个适用的新稳定版本以 `docs/releases/vX.Y.Z.md` 作为唯一用户正文来源。文件必须在触发发布的提交中存在，workflow 不生成、补写或提交正文；`docs/releases/v0.1.0.md` 只作为当前结构的正向样本，本计划不据此决定或执行一次正式发布。

**理由**：按版本保存可以让仓库历史、tag 和公开正文一一对应，也避免发布阶段从 commit 或审计数据临时推导功能范围。首次适用版本仍须在发布准备时由用户明确目标版本和对应规格。

**考虑过的替代方案**：单一 `CHANGELOG.md` 需要在发布时切片；workflow 生成并回写会产生递归触发；SubTandem 从 v0.1.0 直接建立版本化正文，无需回填其他 Release 记录。

## 用户正文语法与语义验收

**决策**：使用不依赖第三方解析器的严格 Markdown 子集。标题必须为 `# SubTandem vX.Y.Z`；其后只能是按“新功能”“功能改进”“问题修复”“升级与兼容提醒”顺序出现的非空章节和中文顶层条目，或唯一的固定无变化句。重复、空白、未知或乱序章节、额外标题、普通正文块、代码块和明确的技术审计字段均失败。

**理由**：小型确定语法足以覆盖当前发布说明，能稳定验证路径、版本、章节和技术证据隔离，不需要新增 Markdown 依赖。每条是否准确描述用户场景、是否来自用户指定且已验收规格无法由语法可靠证明，继续由 `iina-plugin-release` 流程和开发者单人核对。

**考虑过的替代方案**：自由 Markdown 无法可靠拒绝空章节和证据页；关键词或模型自动判断语义会产生误报并伪装成验收；front matter、HTML 注释或额外追溯清单会污染直接发布的用户正文。

## 共享校验边界

**决策**：新增单一共享模块负责路径派生、正文解析、原始 SHA-256 和远端比较规范化。元数据、最终审计和发布接口复用该模块；正文的远端相等只规范化 CRLF 为 LF 并忽略结尾空白，其他字符和结构差异均视为冲突。

**理由**：三个边界都需要验证同一份正文。共享纯规则避免各脚本分别实现后漂移；最小规范化兼容 GitHub CLI 对行尾和末尾换行的处理，同时保留正文内部差异的可见性。

**考虑过的替代方案**：只在元数据阶段验证无法防止后续产物漂移；逐字节比较远端正文会因行尾产生误报；全面 trim 或重排 Markdown 会掩盖真实正文差异。

## 跨任务正文绑定

**决策**：元数据阶段读取权威文件并输出相对路径与原始摘要；最终归档审计在全部构建步骤后重新读取、复验并核对初始摘要，再原样复制为 `build/release/release-notes.md`，把源路径和摘要写入 `release-audit.json`。发布阶段验证审计副本摘要后再进行任何远端写入。

**理由**：构建和发布位于不同任务。经审计的副本使发布任务只消费已经验证的不可变工作流产物；初始与最终摘要比较证明正文仍来自触发提交，而不是构建期间被改变的另一份合法文档。

**考虑过的替代方案**：发布任务直接读取第二次 checkout 的文件较简单，但正文不属于审计产物；只复制不记录摘要不能证明跨任务一致；把正文加入公开附件会产生重复且不必要的下载资产。

## 技术发布证据位置

**决策**：删除审计脚本生成技术 Release 正文的能力。安装包身份、大小、摘要、门禁、归档清单、helper、FFmpeg 和三项 IINA 宿主未覆盖状态继续写入 `release-audit.json`，并在 Actions 摘要与日志中可读；安装包和 FFmpeg 校验文件继续作为现有公开资产。用户正文不含这些字段。

**理由**：技术证据仍需可追溯，但 GitHub Release 正文的读者需要的是功能变化。结构化审计和 Actions 记录适合维护者核对，也不会把过程数据混入版本化用户文档。

**考虑过的替代方案**：在技术证据前追加用户摘要仍混合两种职责；删除技术证据会削弱可信发布；把完整审计 JSON 新增为公开资产会改变既有四项资产契约。

## 打赏入口边界

**决策**：Release 正文不再固定追加“自愿支持”章节，因为 009 只允许四类功能变化章节。爱发电与 Ko-fi 继续通过七份 README 和 GitHub Sponsor 入口提供；006 中要求 Release 打赏段落的当前规格、计划、研究、模型、契约与验证说明在实施时直接收敛，已完成任务记录保持不删不改编号。

**理由**：保留第五类段落会直接违反新规格，并让每份版本功能说明混入与该版本变化无关的长期推广内容。README 和 Sponsor 已提供稳定入口，不影响项目接受自愿支持。

**考虑过的替代方案**：在每份版本文件人工保留打赏段落不符合允许章节；发布器自动拼接会使公开正文不再直接来自版本文件；在 009 中记录“旧规则已替代”会违反 SDD 只描述当前意图。

## Draft、公开版本与正文冲突

**决策**：draft 继续只有在 tag、目标提交、正文和资产一致时恢复。公开稳定版本只有在规范化正文与当前版本化正文一致时才安全跳过；正文不同则报告冲突并保持零远端写入。公开 tag 不与同版本后续 `main` 提交比较；新发布完成后仍复核触发提交、Latest、正文和资产。

**理由**：正文偏差必须可见，但同版本后续提交不能移动已公开 tag。只比较公开正文既保持不可变，也允许未提升版本的正常验证和跳过。

**考虑过的替代方案**：公开版本无条件跳过会隐藏正文漂移；自动编辑公开正文会破坏不可变契约；要求 tag 指向每次后续提交会让同版本验证永久失败。

## 当前 SDD 与稳定文档收敛

**决策**：009 拥有版本化正文契约；004 继续拥有通用门禁、资产、权限、审计和 Release 生命周期，并引用 009；006 继续只负责冻结的 README 与 Sponsor 入口；005 负责 v0.1.0 首版合规发布。`docs/validation/package.md` 区分用户正文和技术证据，`docs/engineering/development.md` 只保留简短入口与引用。

**理由**：项目治理要求 SDD 只描述当前意图，同时要求既有 `tasks.md` 的已完成任务全部保留。由新功能拥有新增契约、旧功能删除冲突的当前要求，可以避免重复状态机和历史叙事。

**考虑过的替代方案**：只在 009 写“覆盖旧规则”会留下互相冲突的当前规格；重写 004 全部发布设计会扩大范围；改造 005 会违反非追溯边界。
