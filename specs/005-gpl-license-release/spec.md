# 功能规格：GPL 许可与首版合规发布

**功能目录**：`005-gpl-license-release`  
**状态**：已完成

## 目标

SubTandem 仓库、包元数据、README 和 v0.1.0 正式安装包必须一致采用 `GPL-3.0-only`，并随包提供项目许可与全部实际分发组件所需的第三方声明。

## 用户故事

### 用户故事 1：确认项目许可（P1）

用户或贡献者可从 README、根许可证与包元数据确认项目只按 GPL 第 3 版授权。

### 用户故事 2：获得合规安装包（P2）

用户下载正式安装包时，可在归档根目录读取 `LICENSE` 与 `THIRD_PARTY_NOTICES.txt`，且包内不包含源码、测试、缓存、凭据或其他禁止内容。

### 用户故事 3：发布合规首版（P3）

维护者通过现有失败关闭的发布流程构建、审计并发布唯一的 v0.1.0；同版本后续执行只读核验，不覆盖已经发布的稳定身份。

## 功能需求

- **FR-001**：仓库必须包含标准 GNU GPL v3 全文，并以 `GPL-3.0-only` 作为唯一 SPDX 标识。
- **FR-002**：README 必须显示 GPL v3 徽章并链接当前仓库的 `LICENSE`。
- **FR-003**：正式包必须在根目录包含与仓库逐字一致的 `LICENSE` 与 `THIRD_PARTY_NOTICES.txt`。
- **FR-004**：打包、校验和最终审计必须要求两份合规文件，并继续拒绝所有禁止内容和不安全归档结构。
- **FR-005**：v0.1.0 必须由当前触发提交、审计正文和审计资产一次性创建；不得覆盖不同 commit 或不同内容的同版本 Release。
- **FR-006**：发布必须公开、非 prerelease、Latest，tag 精确指向触发提交。
- **FR-007**：发布失败不得留下被报告为成功的半成品 Release。
- **FR-008**：变更不得改变插件运行时、权限、字幕数据流或翻译行为。

## 成功标准

- 仓库、npm 元数据、README 与正式归档的许可身份 100% 一致。
- 正式归档包含两份必需合规文件，现有安全审计全部通过。
- v0.1.0 tag、Release 正文、资产和 SHA-256 与触发提交的审计结果一致。

## 假设

- `@noble/hashes 2.3.0` 与锁定 FFmpeg 是当前需要随分发材料披露的非系统组件。
- 系统 libcurl 由 macOS 提供，不作为安装包中的第三方二进制分发。
