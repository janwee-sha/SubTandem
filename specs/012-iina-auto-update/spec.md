# 功能规格：IINA 自动更新发现

**功能目录**：`specs/012-iina-auto-update`  
**创建日期**：2026-08-19  
**状态**：已完成

**输入**：为 SubTandem 0.1.0 修复 IINA 自动更新发现；作为独立完整 SDD 变更交付。

## 用户场景与测试

### 用户故事 1：后续版本可由 IINA 发现（优先级：P1）

用户通过 GitHub 或正式安装包安装 SubTandem 0.1.0 后，希望以后可以使用 IINA 的插件更新检查发现并安装更新，无需每次手动寻找下载文件。

**优先级理由**：可持续更新是加入 IINA 社区插件列表后的核心维护能力。

**独立测试**：安装正式 0.1.0 包并检查其更新身份；将一个更高的受控发布身份与其比较时，应识别为可用更新，相同或更低身份不得触发更新。

**验收场景**：

1. **假如** 用户安装正式 0.1.0 包，**当** IINA 读取插件信息，**那么** 插件具有指向 `janwee-sha/SubTandem` 的有效更新来源和可比较的更新序号。
2. **假如** 更新来源提供更高更新序号，**当** 用户在 IINA 中检查更新，**那么** IINA 能识别新的 SubTandem 版本并从该仓库的最新正式 Release 安装它。
3. **假如** 更新来源的更新序号相同或更低，**当** 用户检查更新，**那么** IINA 不提示错误的升级。

---

### 用户故事 2：发布版本不会遗漏更新序号（优先级：P2）

维护者准备新的稳定版本时，希望发布门禁同时校验用户版本与更新序号，防止出现 Release 已发布但 IINA 无法发现的版本。

**优先级理由**：单次修复只有在后续发布不会再次遗漏更新元数据时才可持续。

**独立测试**：分别提供匹配、缺失、非法和与版本不一致的更新身份；只有匹配的稳定版本可以进入正式打包与发布。

**验收场景**：

1. **假如** 所有项目版本为 0.1.0 且更新身份匹配，**当** 发布门禁运行，**那么** 元数据校验通过并进入后续打包。
2. **假如** 更新仓库、更新序号缺失或非法，**当** 发布门禁运行，**那么** 在公开 Release 前失败并指出不一致字段。
3. **假如** 稳定版本已提升但更新序号仍属于旧版本，**当** 发布门禁运行，**那么** 发布失败且不会产生不可发现的新 Release。

---

### 用户故事 3：首版用户获得更新指引（优先级：P3）

安装 SubTandem v0.1.0 的用户希望确认该安装已经具备 IINA 更新身份，并了解后续更新的检查方式。

**优先级理由**：首版即提供一致的更新身份，确保后续版本可以持续由 IINA 发现。

**独立测试**：阅读安装说明和 v0.1.0 发布说明即可确认首版已包含更新身份，以及后续版本由 IINA 检查。

**验收场景**：

1. **假如** 用户安装 v0.1.0，**当** 阅读安装说明，**那么** 能确认该版本已包含 IINA 更新元数据。
2. **假如** 用户准备检查后续版本，**当** 阅读更新说明，**那么** 能确认可使用 IINA 的插件更新检查。

### 边界情况

- 更新来源不存在、不可访问或返回无效插件信息时，不得把当前安装误判为可更新。
- 最新 Release 缺少合法 `.iinaplgz` 时，不得声称更新安装成功。
- 版本号提升但更新序号未提升、倒退或超出允许范围时，正式发布必须失败。
- 更新仓库与实际公开仓库不一致时，安装包必须被拒绝。

## 需求

### 功能需求

- **FR-001**：正式 0.1.0 安装包必须声明唯一的 SubTandem 更新仓库和正整数更新序号。
- **FR-002**：更新仓库必须精确指向公开的 `janwee-sha/SubTandem` 仓库。
- **FR-003**：更新序号必须随每个稳定版本严格递增，并能由当前稳定版本唯一确定。
- **FR-004**：发布门禁必须拒绝缺失、非法、仓库不匹配或与稳定版本不一致的更新身份。
- **FR-005**：正式归档中的更新身份必须与仓库源清单、目标版本和产物名一致。
- **FR-006**：从 GitHub 安装或更新时必须继续使用经过现有发布门禁审计的最新正式 `.iinaplgz`，不得引入源码安装或额外下载源。
- **FR-007**：0.1.0 用户文档必须说明 IINA 的更新检查入口以及网络或 Release 不可用时的失败边界。
- **FR-008**：v0.1.0 发布说明必须说明 SubTandem 是全新插件身份，并确认首版已包含后续版本所需的更新元数据。
- **FR-009**：本功能不得改变字幕、凭据、Provider、权限、播放、缓存或翻译行为。
- **FR-010**：自动化验证必须直接检查生产清单、发布元数据接口和正式归档，不得仅断言文档文字或文件存在。

### 关键实体

- **更新身份**：由公开仓库、用户版本和严格递增更新序号组成，供 IINA 判断是否存在更新。
- **更新来源**：IINA 读取当前插件信息并下载最新正式安装包的公开 GitHub 仓库。
- **首版安装**：具有合法 v0.1.0 更新身份、可由 IINA 检查后续正式版本的安装。

## 成功标准

### 可度量结果

- **SC-001**：正式 0.1.0 归档中的版本、更新仓库和更新序号校验通过率为 100%，三者任一缺失或不一致时可发布产物数量为 0。
- **SC-002**：对相同、较低和较高三个更新身份执行比较时，只有较高身份被识别为可用更新，误报数量为 0。
- **SC-003**：未来稳定版本只提升用户版本而未同步提升更新序号时，发布门禁在公开 Release 前失败率为 100%。
- **SC-004**：0.1.0 正式包通过现有八项发布门禁，包内新增源码、权限、网络目的地、运行时数据或敏感材料数量为 0。
- **SC-005**：首版用户可在一份安装说明中确认更新元数据已启用并找到后续更新检查方式。

## 范围边界

- 不修改 IINA 应用或其上游仓库的更新实现。
- 不创建或维护额外兼容分支，不改变 SubTandem 的默认分支。
- 不自动发布、push、创建 tag 或修改现有 GitHub Release；本功能只准备并验证 0.1.0 发布候选产物。
- 不改变或扩大插件更新身份之外的运行时数据边界。
- 不改变插件的运行时功能、权限和隐私边界。

## 假设

- IINA 1.4.4 继续使用插件清单中的更新仓库和整数更新序号判断更新，并优先安装最新正式 Release 中的 `.iinaplgz`。
- GitHub 继续为公开仓库提供 IINA 当前使用的默认分支兼容读取行为；该行为与 IINA 官方插件的发布方式一致。
- 0.1.0 是首个包含 SubTandem 更新身份的稳定版本。
- 每个稳定版本只对应一个不可变的更新身份和一个公开正式 Release。
